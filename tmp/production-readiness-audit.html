A production-readiness audit is not a design review. It is a structured inspection of everything that has to hold up once the app is live: security, backend, data, performance, stability, and the release process itself. Here are the ten checks we run on every app, in plain words.

TL;DR: A production-readiness audit covers ten areas: security, backend, database, performance, crash reporting, code quality, the release process, analytics, third-party services, and store and legal readiness. For each area we list what is verified, the red flags, and what to do when the audit finds trouble.

The audit matters most at two moments: right before launch, and right after you inherit an app someone else built. It answers one question: is this app safe to put in front of real users?

1. Security Foundations

Security is the check that gets skipped most and hurts most when it is missing. An app that "works fine" can still leak data, and you find out about it from an angry customer, not from your dashboard.

What a real audit verifies:

  • Authentication and sessions are handled correctly. Tokens expire, logins cannot be bypassed, password resets are safe, and old sessions actually die when a user logs out.
  • No secrets live inside the app code. API keys and tokens belong on the server, never baked into the app where anyone can extract them.
  • Sensitive data is encrypted in transit and at rest. That means HTTPS everywhere, no HTTP calls hiding in a corner of the code, and proper storage for things like tokens and personal data.
  • The API cannot be abused by anyone who finds it. Endpoints check who is calling, rate limits exist, and a user cannot see another user's data by changing an ID in a request.

The red flag: your team has never worked through this list. An experienced engineer finds most of these in a day. A founder discovers them the hard way.

2. Backend and API Health

The backend is what the app stands on. A mobile app audit has to include the server side, because that is where outages and data loss actually happen.

What a real audit verifies:

  • Errors are handled, not hidden. Failed requests get proper error responses, timeouts are sane, and one slow service degrades gracefully instead of taking the whole app down.
  • Rate limiting and abuse protection exist. Without them, one misbehaving client or one attack can knock the API over.
  • Background work runs in the background. Emails, uploads, reports, and notifications should never block a user's request from completing.
  • The API behaves predictably under load. It has been tested with realistic traffic before real users arrive.

The red flag: the backend runs on a single server nobody has stress-tested, and "we will scale when we need to" is the entire scaling plan.

If load questions come up, our scaling readiness checklist covers what to check before a big push.

3. Database and Data Safety

Data is the one thing you cannot get back. An audit treats the database as the most precious part of the whole system, because it is.

What a real audit verifies:

  • Backups exist and have been tested. A backup you have never restored is a rumour, not a backup.
  • Migrations are controlled. Database changes are versioned and reversible, not run by hand on the live server and hoped for the best.
  • Indexes match real queries. Slow screens are often slow because the database is scanning millions of rows for every request. A quick review of query patterns against indexes finds this in an afternoon.
  • Data retention and privacy rules are respected. Old data gets cleaned up, deleted accounts actually get deleted, and personal data is not kept forever "just in case."

The red flag: nobody can say when the last successful restore test was. That is the scariest sentence in a data audit.

4. Performance and Load Times

Slow apps do not get second chances. A production readiness audit measures performance on real devices and real networks, not on the office wifi.

What a real audit verifies:

  • Key screens load fast. Main screens render in under 3 seconds on a mid-range phone. Key API calls respond in under 500 milliseconds at the 95th percentile.
  • Caching is used where it should be. Images, config, and repeat requests should not hit the server every single time.
  • Assets are the right size. Nobody needs a 4000-pixel photo inside a 200-pixel thumbnail, and oversized assets are the most common cause of slow first launches.
  • The app behaves well on poor networks. Timeouts, retries, and offline states are designed, not accidental. A user on a train should get a graceful message, not a frozen screen.

The red flag: the team has never measured actual load times. "Feels fast" is not a strategy.

5. Crash Reporting and Stability

You cannot fix crashes you cannot see. A shocking number of apps go live with no crash reporting at all, which means the team learns about crashes from one-star reviews.

What a real audit verifies:

  • Crash reporting is installed and working. Tools like Sentry or Firebase Crashlytics are set up on every platform, symbols are uploaded so crashes are readable, and someone actually looks at the reports.
  • The crash-free rate is healthy. For a production app, 99.9% of sessions crash-free is the bar. Below 99% means 1 in 100 sessions crashes.
  • Errors are grouped and prioritised. The top five crashes should be known by name. If the team cannot list them, nobody is reading the reports.
  • Release tracking is in place. Each new version gets watched for new crashes, so a bad release is caught in hours, not weeks.

The red flag: there is no crash dashboard, or nobody opens it. Every crash your users hit is invisible to you.

6. Code Quality and Architecture

This is the check that answers the big question: was this app built to last, or built to demo? A production-readiness audit reads the code the way a building inspector reads a foundation.

What a real audit verifies:

  • Frameworks and dependencies are current and supported. Outdated frameworks stop getting security fixes.
  • The architecture is organised and understandable. A new engineer should be able to find things. If the original team is the only team that can touch the code, you do not own your app, you rent it from them.
  • Dead code and abandoned experiments are cleaned up. Half-finished features are where bugs hide.
  • Dependencies are justified. Every third-party library is a commitment: it can break, get abandoned, or ship a security hole. The audit lists them and asks which ones are actually earning their place.

The red flag: upgrading anything breaks everything, and only one person understands how it all fits together. That is not a codebase. That is a hostage situation.

If the foundations are solid, fixing is usually the right move. If they are not, rebuilding is cheaper than patching forever. Our rebuild vs refactor guide covers the five-foundation check we use to decide.

7. Update and Release Process

The audit checks the machinery of shipping, not just the code being shipped.

What a real audit verifies:

  • You can ship urgent fixes fast. Over-the-air updates let you push fixes without waiting for store review.
  • There is a real release process. Builds are tested before they go out, someone approves releases, and the process is written down rather than living in one person's head.
  • Rollback is possible. If a release breaks something, the team can revert quickly. If the only option is "fix forward and hope," the release process is incomplete.
  • Beta and staged rollouts exist. New versions reach a small group first, so problems surface with a hundred users instead of a hundred thousand.

The red flag: releases happen when someone feels brave. The process is the product here.

8. Analytics and Observability

Analytics and observability are how you see the app's health once it is live. Their absence is a finding in itself.

What a real audit verifies:

  • Key events are tracked. Signups, purchases, core actions: the events that tell you whether the app works as a business.
  • Funnels and drop-offs are visible. If users vanish between two screens, someone should be able to see where and how many.
  • Server-side logging and monitoring exist. The team gets alerted when error rates spike or the database slows down, rather than finding out from customers.
  • Session recordings or replays are available for debugging. Watching what a frustrated user actually did is worth a hundred bug reports.

The red flag: the only analytics are download counts. You know how many people installed the app and nothing about what they do in it.

9. Third-Party Services and SDKs

Modern apps are assembled from services: push, payments, maps, analytics, auth. Each one has its own keys, bills, and failure modes. The audit inventories all of them.

What a real audit verifies:

  • Every service is documented. Someone can list every third-party account the app depends on, who owns it, and what it costs.
  • Keys and credentials are managed properly. They are rotated, scoped, and stored safely, not shared in a team chat.
  • Unused SDKs are removed. Every unused SDK adds weight, startup time, and a potential security hole. Apps accumulate them like junk drawers.
  • Critical paths have fallbacks. If the payment provider has an outage, the app should fail gracefully instead of freezing at checkout.

The red flag: nobody knows the full list. Services get added by whoever needed them and are never removed when they stop being needed.

10. Store and Legal Readiness

The last check stops launches cold: the app stores and the law. An app can be technically perfect and still get rejected or pulled.

What a real audit verifies:

  • Privacy policy and terms exist and are accurate. They describe what the app actually collects, not what a template said.
  • App permissions are justified. Every permission the app requests matches a real feature, because both stores now reject apps that ask for more than they need.
  • Store guidelines are followed. Screenshots, descriptions, and content policies meet Apple and Google requirements.
  • Developer accounts, signing keys, and store listings belong to the founder or the company, never to the agency that built the app.

The red flag: the agency that built the app owns the store account, and the founder does not have the login. Fix that before anything else.

What Happens After the Audit

A production-readiness audit ends with a report, not with anxiety. The report lists every finding, ranks them by risk, and says what to fix first. Most apps we audit do not need to be rebuilt. They need a prioritised list of real problems, fixed in the right order: security and data first, then stability, then performance, then polish.

The pattern: surface problems with sound foundations mean fix, and it usually takes less time than founders fear. Deep problems, wrong architecture, missing security, untrustworthy data, mean secure the data and rebuild cleanly. Either way, the audit tells you which situation you are in, instead of guessing.

Frequently Asked Questions

How long does a production-readiness audit take? For a typical app, two to three days with two to three engineers. The code review is the biggest part, then the security and backend checks. Very large or messy codebases take longer.

When should I run a production-readiness audit? Three moments matter most: right before launch, right after inheriting an app from another agency, and before any major growth push.

How is a production-readiness audit different from a code review? A code review looks at code quality in isolation. A production-readiness audit looks at the whole system: code, backend, database, security, release process, analytics, third-party services, and legal readiness. It answers whether the app is safe to run, not just whether the code is tidy.

What does a production-readiness audit cost? It depends on the app's size. We offer ours for free, in exchange for a testimonial if the report is genuinely useful. Most agencies charge a real fee, and it is worth paying, because what it finds usually saves far more than it costs.

My agency says the app is ready. Should I still get an audit? Yes, from someone independent. Your agency did the work, which means they have blind spots about it. Every founder we have met who skipped the independent check says the same thing afterwards: the problems were obvious to fresh eyes.

What if the audit finds that my app needs to be rebuilt? Then you want that answer before launch, not after. Rebuilding with your data secured and migrated is far cheaper than rebuilding after a public failure.
