A founder taking over an app usually gets a link to a code folder, a password in a chat message, and good luck. Two weeks later the new team tries to ship a fix and discovers the real handover never happened. The store account belongs to the old developer. The signing key is on a laptop nobody can reach. The backup has never been tested.

That is why an app handover checklist matters. When you take over app from another developer, the code is only one of seven things changing hands. This guide lists 42 items in seven groups, the tests that prove each group transferred, and a five day plan.

TL;DR: A complete handover covers code and build, store accounts and signing keys, backend and data, third party services, payments and analytics, designs and documents, and contracts and close out. Judge it by three tests: you can log in as owner, the new team can build and release, and a backup can be restored. If any test fails, the handover is not finished.

The seven groups at a glance:

  1. Code and build. Repository, history, backend code, admin code, build instructions, release process.
  2. Store accounts and signing. Apple account, Google Play account, app transfer, certificates, keystore, identifiers.
  3. Backend, data and backups. Hosting, database, backup, restore test, file storage, scheduled jobs.
  4. Third party services. Maps, email, messaging, push, crash reporting, API key register.
  5. Payments, analytics and growth. Payment account, subscriptions, analytics, ad accounts, domain and DNS.
  6. Designs, documents and knowledge. Design files, brand assets, architecture notes, known issues, test accounts.
  7. People, contracts and close out. IP assignment, licences, invoices, access removals, renewal dates, sign off.

1. Why Most Handovers Fail Even When the Code Arrives

Code can be copied. Everything around it is held in accounts, and accounts transfer only when an owner takes a specific action. That gap is where takeovers stall.

The failures we see most often:

  • Guest access mistaken for ownership. A founder added as a user assumed the app was theirs. Guest access can be removed in one click.
  • One missing key blocks every release. The keystore or certificate is missing, so no update can ship as the same app.
  • Secrets shared in chat, never recorded. Nobody kept a register, so nobody knows the full list to rotate.
  • Knowledge never written down. Why a workaround exists and which integration is fragile is in no document.

Our guide on what to do when your developer disappeared covers the emergency version. This post is the planned version, while both sides are still talking.

A handover is not a delivery. It is a transfer of control, and control is proven by logging in, building, and restoring, not by receiving files.

2. Group One: Code and Build, Items 1 to 6

Collect these six:

  • Item 1, the full repository in your organisation. GitHub, GitLab or Bitbucket, transferred into an account your company owns. A download of the latest files is not a repository.
  • Item 2, the complete history and branches. Commit history and active branches, which explain why the code looks the way it does.
  • Item 3, every codebase, not just the app. Mobile app, backend or API, admin panel, website and background scripts.
  • Item 4, build instructions a stranger can follow. Tools, versions, local setup and how to produce a release build.
  • Item 5, environment and configuration, listed by name. Settings for development, staging and production, with real values in a secure vault, never in the code.
  • Item 6, the release process, written down. Approval, testing, submission and rollback.

Verification test: a developer who did not build the app builds it on a clean machine using only the written instructions. Any question they have to ask the old team is a gap to fix while that team is still available.

3. Group Two: Store Accounts and Signing, Items 7 to 12

Whoever controls the store accounts controls the live app. Settle this group first if anything else has to wait.

Collect these six:

  • Item 7, the Apple Developer account in your company name. You as Account Holder. Only the Account Holder can transfer the app, change banking and renew the programme.
  • Item 8, the Google Play Console account in your company name. Owner access for you, admin access listed person by person.
  • Item 9, the app transfer, if the app sits in the wrong account. Both stores support transfers, and both sides must act. Start early.
  • Item 10, Apple certificates and provisioning profiles. With expiry dates noted.
  • Item 11, the Android keystore and upload key position. Know whether Play App Signing is enabled and where the upload key is held. With Play App Signing, a lost upload key is an owner reset request. Without it, a lost key can be permanent.
  • Item 12, bundle ID, package name and listing assets. Identifiers in your accounts, plus listing text, screenshots and artwork in original files.

Verification test: log in to both consoles as owner and confirm you can see agreements, banking and release history. If you can only view the listing page, you do not control the app yet. That is the core of transfer app ownership, control follows the accounts, not the code folder.

4. Group Three: Backend, Data and Backups, Items 13 to 18

The backend is where your users actually live. Code can be rebuilt. Lost user data usually cannot.

Collect these six:

  • Item 13, the hosting account in your name. AWS, Google Cloud, Firebase or similar, your card on billing, you as owner.
  • Item 14, the production database, with owner access. You can log in and export it. Data you cannot export is data you do not fully own.
  • Item 15, the backup schedule, in writing. Frequency, location and retention.
  • Item 16, a restore test, actually performed. Restore the latest backup into a separate environment and open the app against it. This is the difference between having backups and hoping you have them.
  • Item 17, file storage and user uploads. User uploads, and proof the app points at storage you control.
  • Item 18, cron jobs, queues and scheduled tasks. Password resets, renewals, reports and cleanup jobs, each with its trigger and failure logs.

If the data shape is sound and the restore test passes, keeping the existing foundation is usually realistic. Our production readiness audit guide covers the deeper checks that follow.

5. Group Four: Third Party Services, Items 19 to 24

Modern apps are stitched together from other companies services. Each one is an account, a key and a bill.

Collect these six:

  • Item 19, maps and location services. The account and key restrictions.
  • Item 20, email and messaging providers. Transactional email and SMS, with sender domains under your control, or your password resets depend on the old developer.
  • Item 21, push notification setup. The push project in your organisation, plus the Apple push key.
  • Item 22, crash reporting and monitoring. Sentry, Crashlytics or similar, with alerts changed to your team.
  • Item 23, any AI or paid API services. Model providers and specialist APIs, billing in your name, limits confirmed.
  • Item 24, the full API key register. One list, every key, what it unlocks, and a rotation plan. After handover, rotate keys the old team could still use.

If a service is not on the register, it does not get transferred, it does not get rotated, and it usually announces itself later by expiring at the worst moment.

6. Group Five: Payments, Analytics and Growth, Items 25 to 30

Founders check the app and forget the money accounts, then discover months later that payouts or analytics history sit elsewhere.

Collect these six:

  • Item 25, the payment account. Stripe or equivalent, in your business name, payouts to your bank account.
  • Item 26, in app purchase and subscription products. Every product, price and subscription group in both stores, matched against payment records.
  • Item 27, analytics, with history preserved. The project in your organisation, history preserved, so before and after can be compared.
  • Item 28, attribution and ad accounts. Install campaigns and attribution tools in your name, data intact.
  • Item 29, store optimisation and review tools. Keyword and review monitoring, plus who receives review alerts.
  • Item 30, domain, DNS and business email. Registrar in your name, DNS access and renewal dates. A lapsed domain can take down a healthy app.

7. Group Six: Designs, Documents and Knowledge, Items 31 to 36

This group decides how fast the new team can move after day one.

Collect these six:

  • Item 31, design files in editable form. Figma or equivalent, in your workspace, including components, not only exported images.
  • Item 32, brand assets. Logos, icons, fonts with licences, colours and artwork source files.
  • Item 33, a short architecture note. How the pieces fit together, where data flows, and why the biggest choices were made. Two honest pages are enough.
  • Item 34, the known issues list, honestly stated. Deferred bugs, fragile areas, workarounds, and what the old team would fix next. Every codebase has this list.
  • Item 35, product documents and roadmap state. The brief, what was promised against what shipped, and what is in progress.
  • Item 36, test accounts and test data. Accounts for every role, sandbox payment details and admin logins.

If items 33 and 34 are weak, expect assessment to take longer. Our guide to rebuild vs refactor explains why.

8. Group Seven: People, Contracts and Close Out, Items 37 to 42

The last group is paperwork. It is also the group that decides ownership if there is ever a dispute.

Collect these six:

  • Item 37, IP assignment confirmed in writing. The contract that says code and designs belong to your company. Payment alone is not the same document.
  • Item 38, open source and third party licences listed. Which libraries the app uses and on what terms.
  • Item 39, final invoices and payment state, agreed. What was paid and what is owed, agreed by both sides.
  • Item 40, old access removed, in the right order. Remove old access only after owner access and the verification tests pass, or you can lock everyone out.
  • Item 41, every renewal date in one calendar. Apple programme, domain, hosting and certificates, with owner for each. Most takeover emergencies in the next year are missed renewals.
  • Item 42, written sign off from both sides. What was transferred, on what date, and that the handover is complete.

9. Score the Handover: Red, Amber, Green

Score each group after the verification tests, not after the files arrive.

How we score a takeover:

  • Green, transfer proven. Owner login works, the test passes, items are in your register.
  • Amber, transfer claimed but not proven. Access was provided, but a test has not run, or an item is still in the old name.
  • Red, transfer blocked. An owner action is missing, a key is lost, or a backup does not restore.

What the score means:

  • No reds, two ambers or fewer. Proceed to assessment and planning. The takeover is real.
  • One red in code, stores or data. Pause new features. Fix that group first, because everything else depends on it.
  • Reds in three or more groups. Treat this as a recovery, not a handover. Our cost to rebuild an app guide shows how that changes the maths.

10. The Five Day Handover Plan

With a cooperating team, a typical founder app can run this in about a week.

  1. Day 1, accounts first. Groups two and seven, store ownership, transfers started, IP and payment state confirmed, renewal dates captured.
  2. Day 2, code and build. Group one transferred into your organisation, and the clean machine build test run and fixed while help is available.
  3. Day 3, backend and data. Group three, owner access, export taken, and the restore test performed, not scheduled.
  4. Day 4, services and money. Groups four and five, key register completed, payment and analytics ownership confirmed, alerts pointed at your team.
  5. Day 5, knowledge and close out. Group six collected, known issues walkthrough recorded, scoring completed, old access removed where safe, and sign off exchanged.

Frequently Asked Questions

What should an app handover checklist include? Seven groups, code and build, store accounts and signing, backend and data, third party services, payments and analytics, designs and documents, and contracts and close out. That is 42 items, each closed by a test, not by a file being sent.

How long does it take to take over an app from another developer? With a cooperating developer, about five working days for a typical founder app. Assessing code quality and planning the next phase usually takes about another week.

What is the most commonly missing item in an app takeover checklist? Signing and release control. Founders recover code and data, then discover the keystore, certificate or Account Holder access is missing, so no update can ship. Check group two on day one.

Do I need to rotate API keys after a handover? Yes. Once owner access is proven and new keys are tested, rotate keys the old team could still use, update the register, and remove old access, in that order, so you do not break live services.

What if the old developer will not hand over the app? Gather the contract and invoices and make a formal written request naming the items in this checklist. Many cases resolve there. If they still refuse, a lawyer is the next step.
