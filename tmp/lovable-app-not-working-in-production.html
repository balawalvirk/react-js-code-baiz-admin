1. Why Preview and Production Are Different Jobs

An AI builder is very good at the visible job. Screens, forms, buttons and a flow that looks complete can appear in hours. Production is the invisible job underneath, and it is where a vibe coded app fix usually has to start.

  • Preview data is polite. Real users have old accounts, duplicate emails, expired sessions and data created by an earlier broken version.
  • Preview settings are forgiving. Many preview setups relax rules that production enforces, so a flow can pass in preview while the live rule quietly blocks it, or allows far too much.
  • Preview payments are not real money. Test mode confirms a card form works. It does not prove a live payment tells your app, unlocks the right account, and stays matched when a payment fails, retries or is refunded.
  • Preview has no strangers. Production has people who lose connection mid action, use old phones, and, in a small number of cases, actively look for data they should not reach.

The preview proved the idea can work once, on a good day. Production has to prove it works safely, for everyone, on a bad day too.

2. First, Stop the Harm: Data Anyone Can Read, and Keys Anyone Can Use

Before you fix a broken screen, check whether anything live is exposed. A login bug annoys users. An open database or a leaked key can harm them, and that harm continues while you debug the screen.

Check these two things first:

  • Can one user read another user data? Sign in as a test user and check profile, order and file screens, shared links, and, if your team knows how, a request with another record identifier. If the app returns data that is not yours, the database security rules are not doing their job.
  • Are secrets sitting in client code? Keys that belong on a server should never ship inside the app or browser code, where anyone can extract them. Our rescue page names this plainly among the problems found in tools like Lovable, Bolt and v0: exposed keys, broken login, payments that do not reconcile, and data anyone can read.

If either check fails, treat it as the first job. Restrict the rule, move the secret to the server, rotate the exposed key, and only then return to functional bugs. Do not post screenshots of keys, tokens or user data in a public place while asking for help.

3. Broken Auth: Works Once, Fails on the Way Back

Auth is the most common bolt app problems complaint, and it usually passes the first test. The first signup works. The failure appears on the return visit.

The return visit failures to test:

  • Session does not survive. The user returns and is logged out, or stuck in a loop between the login and home screens.
  • Verification never completes. A confirmation link, magic link or one time code arrives late, expires too fast, points at the preview address, or confirms an account the live app cannot find.
  • Password reset breaks the account. The new password is accepted, and the user still cannot sign in, because reset and login are not talking to the same record.
  • Social and email sign in create two people. The same person ends up with two accounts, one holding their payment and data.
  • A logged out user can still act. Old sessions stay valid after a password change or account closure.

Test auth the way a real user lives it: sign up, sign out, sign back in, reset the password, return the next day, and try on a second device.

If login only works the first time, you do not have a login system yet. You have a signup demo.

4. Database Security Rules: The Door Was Left Set to Preview

In many AI built apps, the database started with rules written for speed of building, not safety. Broad access makes every screen easy to wire up during the build. In production, that same broad access is the problem.

Signs your rules never got tightened:

  • A list loads more records than that user owns. The screen may display only their own, while the request already returned everyone else data to the device.
  • Creating works, but editing your own data fails, or the reverse. Rules written screen by screen, instead of by ownership, produce this uneven pattern.
  • Admin actions work from a normal account. The role check lives only in the visible interface, not in the rule itself.
  • Rules were never tested with a second account. Most rule problems are invisible with one test user, because there is no other person data to leak.

The fix is methodical. List what each user type should read, create, change and delete, by data type. Write rules to that list, then test every line with two normal accounts and one admin account.

5. Payments and Webhooks: Paid, But Nothing Happened

A payment has two halves. The first is the one users see: enter a card, confirm, get a success message. The second is the one that matters: the provider tells your app what happened, through a webhook, and your app updates the account. Most production payment failures live in that second half.

Where the second half usually breaks:

  • The webhook points at the wrong address. It still points at a preview address, so live payments arrive and your live app never hears about them.
  • Test mode and live mode are mixed. The app takes a live payment while listening for test events, so records never match.
  • The success screen is trusted instead of the webhook. The app unlocks because the user reached a thank you page, not because the provider confirmed the money.
  • Retries create duplicates. A provider retries an event, as designed, and the app creates a second order or credit.
  • Refunds and failed renewals change nothing. Money goes back, or a renewal fails, and access stays wrong in either direction.

Reconcile one real transaction by hand before you change anything. Follow it from provider record to webhook event to account change. Where that chain stops is where your bug lives.

6. The Production Gap Triage: Run These Five Steps in Order

This is the tool we want you to keep. When an ai built app not working report lands, order matters. Founders start with the screen a user complained about. Engineers who rescue these apps start with harm, proof and layer.

  1. Stop the harm. Check the two exposures in section 2 first. If either is live, restrict, move and rotate before any other work.
  2. Prove the break with one real path. Walk one failing journey, signup to login to payment to access, on the live app, on a real device, with a fresh account. Write down the exact step where the result stops matching the promise.
  3. Trace the layer. Decide which layer owns that break: auth, database rules, payment webhook, environment settings, or the screen itself. Sections 3 to 5 give you the test for each. Do not let a screen fix stand in for a rule or webhook fix.
  4. Test with a second account and a second day. Repeat the path with a different account, then return later. Many production failures only appear on account two or day two.
  5. Read the verdict honestly. If the breaks are in settings, rules and one or two flows, and the foundations are sound, you have a fix job. If weak foundations show everywhere, you may have a harden or rebuild job. Section 7 explains that read.

Keep the notes from steps 2 to 4. A short record of one proved break, with the layer traced, is worth more than a long list of screenshots and guesses.

Do not ask, is my app broken. Ask, which layer broke, on which real path, proved with which account. That question has an answer you can act on.

7. Fix, Fix and Harden, or Rebuild: How to Read the Verdict

Not every broken AI built app needs to start again, and not every one can be patched into safety. The honest sequence on our rescue page is a free check, then a written verdict, fix, fix and harden, or rebuild, then a written quote.

  • Fix, when the foundations are sound. The breaks are specific: a webhook address, a rule that was never tightened, a session setting, a reset flow. Fix those, test the full path again, and ship.
  • Fix and harden, when the app works but production standards were never applied. Rules need rewriting by ownership, secrets need moving to the server, payments need to trust webhooks instead of screens, and auth needs the return visit tests. This is the most common verdict for a preview built app that found real users.
  • Rebuild, when the foundations are missing. If the data model cannot protect ownership, auth is tangled across duplicate accounts, and every change breaks another flow, patching costs more than it saves. A production grade rebuild sits in the $60,000 to $120,000 or more range on our published pages. Our cost to rebuild an app guide walks through that decision maths.

There is no honest price for a fix or harden pass before the check. The same symptom, paid but not unlocked, can be a one setting webhook fix or a sign that payment handling was never built. Anyone who prices your rescue before tracing the layer is guessing with your money. If a tightly scoped validation build is the right restart instead, that first version sits at $10,000 to $20,000. That is a narrow first version decision, not a rescue price.

8. What a Proper Fix Looks Like, Step by Step

  1. Secure first. Tighten data access by ownership, move secrets to the server, rotate anything exposed, and confirm with a second account that other user data is no longer reachable.
  2. Fix auth as a system. Test signup, sign out, sign in, reset, verification, a second device and a return visit as one connected system, not separate screens.
  3. Repair the payment chain. Point webhooks at the live app, separate test and live modes, make the webhook the source of truth for access, and handle retries, refunds and failed renewals without duplicates.
  4. Set the production environment properly. Live addresses in every link and callback, live keys only on the server, error reporting on, and backups for data you cannot afford to lose.
  5. Retest the whole path, not just the fix. Walk signup to payment to access with two accounts, on real devices, including unhappy paths: expired code, failed card, lost connection, refund.
  6. Write down what changed. Rules changed, settings corrected and paths tested, so the next person does not have to rediscover any of it.

9. What Not to Do When Production Breaks

  • Do not keep reprompting and redeploying blind. Each generated change can fix one screen while quietly changing a rule or flow that was working.
  • Do not test only with your own account. It was created during the build, often with special access or old data. Most production breaks hide from it and hit new users first.
  • Do not call test mode proof. A test payment and a preview login prove the preview. Live mode, a fresh account and a real device prove production.
  • Do not leave a known exposure for later. An app with readable user data is not nearly done. It is actively unsafe.
  • Do not pay for a rebuild before a written verdict. Equally, do not pay for patch after patch once the verdict is clearly rebuild. Both mistakes come from skipping the check.
